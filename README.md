# Где животное — backend

Техническая основа API: Node.js 24 LTS, TypeScript, Fastify, PostgreSQL/PostGIS,
Drizzle и Zod. Схемы запросов и ответов валидируются Zod и публикуются в OpenAPI.

## Подготовка

Нужны Node.js 24, npm и Docker с Compose v2. Версия Node указана в `.nvmrc`.

```sh
npm ci
cp .env.example .env
cp .env.test.example .env.test
```

В `.env` замените оба `replace-with-generated-password` одним случайным паролем,
а в `.env.test` — оба `replace-with-generated-test-password` другим паролем.
Для генерации каждого пароля можно использовать `openssl rand -hex 24`.
Настоящие пароли и файлы окружения не коммитятся.

`DESCRIPTIONS_ENABLED` управляет публикацией новых непустых описаний: при `false`
API возвращает `422 DESCRIPTION_DISABLED`. По умолчанию описания разрешены.

## Локальный запуск

```sh
npm run db:up
npm run db:migrate
npm run dev
```

`db:migrate` последовательно применяет ещё не выполненные SQL-миграции из
`drizzle/` к `DATABASE_URL` из `.env`. Повторный запуск безопасен: Drizzle хранит
историю применённых миграций в БД. Начальная миграция создаёт PostGIS, таблицы,
ограничения и индексы, следующая — заполняет двуязычный справочник животных.

После согласованного изменения Drizzle-схемы новая миграция создаётся командой:

```sh
npm run db:generate
```

Созданную миграцию нужно проверить до применения; уже применённые файлы миграций
не изменяются.

Сервер слушает `127.0.0.1:3000`. Перед открытием порта проверяется подключение
к БД и доступность PostGIS. OpenAPI 3.1 доступен по `GET /openapi.json`.
При SIGINT/SIGTERM сервер закрывает HTTP-соединения и пул БД.

Прикладное API доступно с префиксом `/api/v1`. Все его маршруты, кроме выдачи
анонимного токена, требуют заголовок `Authorization: Bearer <token>`.
Размер JSON-тела ограничен 16 KiB; превышение возвращает
`413 PAYLOAD_TOO_LARGE`.

`GET /api/v1/animals` возвращает активные записи справочника. Для каждой
записи доступны UUID для создания и фильтрации наблюдений, стабильный `slug`
для связи с фронтендовым SVG и русское и английское названия.

`GET /api/v1/config` возвращает публичные настройки интерфейса:
`descriptionsEnabled`, `noteMaxLength` и `mapResultLimit`. Антиспам-пороги и
служебные настройки в ответ не включаются.

## Наблюдения

`POST /api/v1/observations` создаёт наблюдение для активного животного и требует
анонимный bearer-токен и UUID в заголовке `Idempotency-Key`. Координаты передаются
как `{ "longitude": ..., "latitude": ... }` в WGS 84. Время `observedAt` задаётся
в RFC 3339 с часовым поясом, не может быть будущим или старше 30 дней. Необязательные
`locationLabel` и `note` нормализуются в NFC и очищаются от пробелов по краям;
пустой результат сохраняется как `null`. После нормализации поля ограничены 300 и
200 кодовыми точками Unicode соответственно. Обнаружение ссылок и телефонных
номеров, а также фильтрация нецензурной лексики пока не применяются.

Идемпотентность действует в пределах клиента 24 часа. Одинаковые повторы, включая
параллельные, возвращают созданное наблюдение с актуальными счётчиками и голосом
текущего клиента; использование того же ключа с другим телом даёт
`409 IDEMPOTENCY_KEY_REUSED`. Ответ имеет единый формат карточки наблюдения:
`id`, `animalId`, `location` с nullable-полем `label`, `observedAt`, `note`, `votes`,
`confirmationPercent` и `userVote`.

Для одного клиента действует адаптивная пауза между успешными публикациями. При
0 публикаций за последние 60 минут следующая разрешена сразу, после 1 требуется
30 секунд, после 2 — 1 минута, после 3–4 — 3 минуты, после 5 и более — 10 минут.
Пауза считается от последней успешной публикации. Отклонённые запросы и успешные
идемпотентные повторы её не продлевают. При ограничении возвращаются
`429 RATE_LIMITED`, заголовок `Retry-After`, `retryAfterSeconds` и `availableAt`.
События старше 24 часов удаляются при обработке новой валидной публикации и не
выдаются через API; гарантированная очистка после простоя относится к ежедневной
задаче жизненного цикла данных.

`GET /api/v1/observations/{id}` возвращает ту же персональную карточку. Неизвестные,
удалённые и истёкшие наблюдения одинаково возвращают `404 OBSERVATION_NOT_FOUND`.
Ответы карточки и создания содержат `Cache-Control: private, no-store`, поскольку
`userVote` зависит от bearer-токена клиента.

`PUT /api/v1/observations/{id}/vote` устанавливает голос текущего клиента. Тело
`{ "value": "confirm" }` подтверждает наблюдение, `"reject"` отклоняет, а `null`
отменяет голос. Повтор того же состояния безопасен и не создаёт дубликатов. Смена
или отмена голоса и чтение актуальных счётчиков выполняются атомарно; ответ имеет
формат той же персональной карточки с `userVote` и заголовком
`Cache-Control: private, no-store`. Для неизвестного, удалённого и истёкшего
наблюдения возвращается единый `404 OBSERVATION_NOT_FOUND`.

`GET /api/v1/observations` возвращает точки для видимой области карты. Запрос
требует `animalIds` с 1–5 различными UUID через запятую, период `1h`, `24h`, `7d`
или `30d` и границы `west`, `south`, `east`, `north`. Точки на границах включаются;
`west > east` означает область, пересекающую 180-й меридиан. Деактивированные
животные остаются доступны для ранее созданных наблюдений.

Ответ отсортирован по времени от новых к старым и содержит счётчики голосов и
процент подтверждений. Возвращается не более 2000 точек; `truncated: true`
означает, что область или фильтры нужно сузить. Курсорной пагинации у карты нет.

## Очистка данных

При старте приложения выполняется догоняющая очистка, затем она запускается каждые
24 часа без перекрытия запусков одного экземпляра. Удаляются наблюдения с
`observedAt` не новее 30 суток, истёкшие записи идемпотентности и выдачи токенов,
а также события публикаций старше 24 часов. Голоса удаляются каскадно вместе с
наблюдениями. Повторный и параллельный запуск нескольких экземпляров безопасен.
Ошибка отдельной очистки журналируется без остановки API; следующий запуск остаётся
запланированным. При штатном завершении приложение прекращает планирование и
дожидается уже начатой очистки до закрытия пула БД.

## Идентификация клиента

`POST /api/v1/clients` выдаёт случайный анонимный токен в формате
`{"data":{"token":"..."}}`. Ответ имеет статус `201` и
`Cache-Control: no-store`. В БД хранится только SHA-256-хеш токена.

Защищённые маршруты принимают `Authorization: Bearer <token>`. Отсутствующий и
неверный токены дают `401` с кодами `CLIENT_TOKEN_REQUIRED` и
`CLIENT_TOKEN_INVALID`. Все ошибки имеют форму
`{"error":{"code":"...","message":"..."},"requestId":"..."}`. Поле
`requestId` позволяет сопоставить ответ с серверной диагностикой; внутренние
ошибки и трассировки клиенту не возвращаются.

С одного IP разрешено не более 10 выдач за скользящие 10 минут. Следующий запрос
создаёт часовую блокировку и получает `429`, код
`CLIENT_ISSUANCE_RATE_LIMITED` и `Retry-After`; повторы не продлевают блокировку.
IPv6 нормализуется до подсети `/64`. Если API находится за reverse proxy, его
IP или сеть нужно явно указать в `TRUST_PROXY` списком через запятую. Не следует
доверять произвольным proxy-заголовкам из интернета.

Запуск собранного приложения:

```sh
npm run build
npm start
```

БД разработки доступна на `127.0.0.1:5433`, имя БД и пользователь — `animals`.
Её данные сохраняются в именованном Docker volume. Остановка без удаления данных:

```sh
docker compose stop db
```

Используется [образ PostgreSQL 17 / PostGIS 3.5](https://github.com/postgis/docker-postgis).
Образ публикуется для amd64; на Apple Silicon требуется эмуляция amd64,
поэтому платформа явно указана в Compose. Это окружение локальной разработки,
а не конфигурация развёртывания.

## Проверки

```sh
npm run check
```

Команда собирает приложение со строгой проверкой типов, запускает ESLint
и unit-тесты Vitest. Unit-тестам БД не нужна.

Отдельная интеграционная проверка настоящей PostgreSQL/PostGIS:

```sh
npm run db:test:up
npm run test:integration
```

Тестовый контейнер использует `127.0.0.1:5434`, пользователя и БД `animals_test`.
Данные находятся в tmpfs и теряются при остановке контейнера. Интеграционный тест
при запуске полностью пересоздаёт схемы `public` и `drizzle`, поэтому принимает
только этот точный адрес через `TEST_DATABASE_URL` и никогда не использует
`DATABASE_URL`. Он применяет миграции на чистой БД и проверяет повторное применение,
PostGIS, SRID, порядок координат, индексы, ограничения и каскадное удаление голосов.
Не подставляйте адрес рабочей БД. Отсутствующее окружение или недоступная БД
приводят к ошибке проверки, а не к пропуску теста.

Остановка тестового контейнера:

```sh
docker compose --env-file .env.test --profile test stop db-test
```
